# Agent context

## Boundaries

- DRF auth template. Preserve URL order/names, response bodies/status, headers, CSRF and cookie semantics. Work on `main`; small `fix:`, `refactor:`, `doc:` commits (docs last). Never push, amend, rebase or bypass hooks. Inspect Git status before editing; do not discard unfamiliar changes.
- Route authority: `app/urls.py` composes `core/{auth,users,registration,password_reset,email_change}/urls.py`; schema/Swagger live in `core/shared/urls.py` (`/api/docs/schema/`, `/api/docs/urls/`). Each feature owns `views.py` (validate/call/respond), `serializers.py`, `services.py` (mutations/transactions/limits). Auth sessions additionally use `core/auth/session_views.py`. Cross-feature imports: `core/models/`, `core/shared/`, or public `core/auth/{services,authenticate,cookies,rate_limit}.py`; never another feature's internals. `core/shared/docs.py` holds response schemas/examples. Never move `core/models/`: Django app label, tables, migrations, UUID user ID and integer session ID depend on its location.
- `manage.py` defaults to dev settings; ASGI/WSGI default to prod. Dev: SQLite + console mail; prod: env-provided `SECRET_KEY`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, optional `DATABASE_NAME`, Secure cookies, SQLite fallback. Use a long random `SECRET_KEY` via env or ignored `.env`. Do not enable `ATOMIC_REQUESTS`: failed code attempts must persist despite HTTP 400.

## Security contracts / traps

- Cookie-only auth (`core/auth/authenticate.py`): access JWT must match active `UserSession`; authenticated unsafe requests require `X-CSRFTOKEN`. `GET /api/login/` issues CSRF cookie (204); `POST /api/login/` requires CSRF, returns only `detail` + HttpOnly access/refresh cookies; bad credentials return **401** via `LoginView.handle_exception` (without it DRF's empty authentication classes turn this into 403). Access cookie name is configurable (`SIMPLE_JWT.AUTH_COOKIE`, default `access_token`), refresh is `refresh_token`; SameSite=Lax, Secure in prod. Cookie creation/deletion belongs in `core/auth/cookies.py`.
- `POST /api/refresh/` enforces CSRF even after access expiry; `SessionService` checks the current refresh JTI/active row, rotates both tokens and updates `last_activity` inside `atomic` + `select_for_update`. SQLite ignores row locking: do not claim race-safety from its tests. Login revokes existing cookie session; same user/device/IP replaces matching sessions. Logout revokes current; revoke-all, self-deactivation, password reset and confirmed email change revoke all; email change/deactivation/revoke-all clear response cookies. Revocation blacklists outstanding refresh tokens and marks sessions inactive; access fails the session lookup. Other-user session IDs return 404; current session cannot be deleted via `/api/sessions/<int:session_id>/`. Do not restore unrouted `UserDetailView`/`UserUpdateSelfView` routes implicitly.
- Registration/reset/email-change use six-digit **hashed** codes, 15-min expiry, five invalid attempts. Verify success does not consume; confirm consumes and mutates atomically; invalid confirm increments must commit outside the inner transaction. Reissue replaces the old code/expiry/usage. Reset sends only to active users but responds identically for unknown email. Email change checks current password and rechecks address uniqueness. Password similarity validator must include custom `User.name` (configured in `app/settings/base.py`). Issuance failure: 503; throttles: 429. `core/auth/rate_limit.py` hashes email/IP: code issuance per scope/email 60 s and IP 2 s; login email 10/5 min, IP 30/5 min. Use `REMOTE_ADDR`, never trust forwarded headers. Default locmem cache is **per process**; production requires shared cache.

## Run / verify

- `pdm install -G dev`; `pdm run dev`/`migrate` (latter mutates DB). `SECRET_KEY=<long-value> pdm run verify` runs check → migration dry-run → schema validation (`--fail-on-warn`, YAML to Unix `/dev/null`) → Ruff → all tests. Individually: `pdm run test tests.test_auth`, `pdm run lint`, `pdm run schema-check`, `pdm run migrations-check`; `pdm run deploy-check` uses prod settings and requires real hosts/key. `pdm run format` changes files; `pdm run ruff format --check` is separate from `verify`. CI uses the same check/test/lint scripts.
- Tests: `tests/base.py` provides CSRF-enforcing `APIClient`, `ApiCase`/`ApiTransactionCase`, login/user/email-code helpers, locmem mail and per-test cache reset. `tests/test_{auth,sessions,users,registration,password_reset,email_change,rate_limit,contracts}.py` map to flows. Read raw codes from `mail.outbox`, never hashed DB values; mock `django.utils.timezone.now` for expiry, but locmem TTL uses monotonic time (`cache.clear()` when testing reissue). Use `TransactionTestCase` for failed-confirmation persistence: outer `TestCase` transaction hides rollbacks. No sleeps/concurrency tests. Last verified full run: 62 tests + check/migration dry-run/schema/Ruff passed; `ruff format --check` passed on 67 files.
- Unverified deployment properties: effective DB locking/concurrency, multi-worker cache throttling, real mail delivery, static serving and production database/hosts/origins. Do not infer production readiness from SQLite tests or Django's check alone.
