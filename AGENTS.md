# Agent context

## Behavioral mandates

- **Strict technical rigor:** Zero tolerance for antipatterns, security vulnerabilities (OWASP ASVS, LGPD, race conditions, PII leaks), unhandled edge cases, or broken contracts.
- **Critical & proactive posture:** Never execute instructions blindly. Challenge assumptions, inspect actual codebase state, assess feasibility, cost, and trade-offs, and propose superior architectural alternatives.
- **AI-optimized documentation:** When creating or updating any documentation (`AGENTS.md`, `docs/*`, plans, specifications), author strictly in English, token-optimized for AI consumption: telegraphic imperative style, high semantic density, structured actionable specs, and zero conversational fluff. Always keep `AGENTS.md` synchronized with codebase boundaries and contracts.
- **No environment variable access:** Never inspect, print, read, or leak system environment variables (`env`, `printenv`, `os.environ`, real values in `.env`).
- **Conditional test execution:** NEVER run test suites (`pdm run test`, `pdm run verify`) autonomously. Run tests ONLY when explicitly commanded by the user, saving compute and time. Static checks (`lint`, `schema-check`) may run as needed.
- **Mandatory end-of-turn report:** Conclude every response with a concise report: (1) changes made, (2) technical rationale and trade-offs, and (3) pending decisions or next steps.

- Settings: `manage.py` defaults to dev (`.env` loaded strictly in dev, SQLite + console mail); ASGI/WSGI default to prod. ## Security contracts & traps

- Cookie-only auth (`core/auth/authenticate.py`): access JWT must match active `UserSession`; unsafe requests require `X-CSRFTOKEN`. `GET /api/login/` issues CSRF cookie (204); `POST /api/login/` requires CSRF, returns only `detail` + HttpOnly access/refresh cookies; bad credentials return **401** via `LoginView.handle_exception`. Access cookie name follows `SIMPLE_JWT.AUTH_COOKIE` (default `access_token`), refresh is `refresh_token`; access path `/`, refresh path `/api/refresh/`; SameSite=Lax, Secure in prod. `clear_auth_cookies` expires the refresh cookie at both paths via separate Set-Cookie headers; login/refresh expire legacy `/` refresh cookies. Cookie ops belong in `core/auth/cookies.py`. Logout and other revocation operations do not require a refresh cookie.
- Refresh & sessions: `POST /api/refresh/` enforces CSRF even after access expiry; `SessionService.refresh_tokens` checks refresh JTI, rotates both tokens, and updates `last_activity` under `atomic` + `select_for_update`. `remember_me` is optional at login and persisted on `UserSession`; standard refresh inactivity is 1 day, remembered inactivity 7 days. Refresh JWT expiry is `min(now+inactivity, session.created_at+absolute)`; access expiry is also capped by absolute limit. Both types retain the existing 30-day absolute cap: reducing the standard cap to 7 days requires explicit approval. Refresh cookie max-age equals remaining JWT lifetime, not a fixed 30-day duration; access/refresh paths and legacy-cookie deletion stay unchanged. A replacement login uses its new `remember_me` flag. Expiry revokes session, clears cookies, returns invalid-refresh 401. Reuse of a signed, unexpired, blacklisted refresh with `session_id` revokes its active session and returns the same 401, including when concurrent refresh requests race. SQLite ignores row locks: do not infer concurrency safety from SQLite. Login revokes existing cookie session; matching user/device/IP replaces session, serialized so concurrent logins cannot create duplicate active matches. Logout and session deletion revoke atomically: refresh-token blacklist and session deactivation must commit or roll back together; cache deletion runs on commit. Revoke-all, self-deactivation, password reset, admin account deactivation, and confirmed email change revoke all and clear cookies. Successful password reset also clears browser auth cookies. Revocation blacklists unexpired refresh tokens and deactivates sessions; purge expired Simple JWT token records periodically with `flushexpiredtokens`, and clean up expired/inactive session rows. Access fails session lookup. Foreign session IDs return 404; current session cannot be deleted via `/api/sessions/<id>/`; deleting another session is a defensive action and does not require password reauthentication. Do not restore unrouted `UserDetailView`/`UserUpdateSelfView`.
- Feature 7 session cache: DB `UserSession` remains source of truth. New access/refresh JWTs carry `session_id`; `CustomAuthentication` accepts a positive `sessions` cache hit only when its `session:{session_id}` entry matches access JTI and user ID; miss/error or legacy token without claim checks DB. Sensitive routes (email change request/verify/confirm, self-deactivation, session deletion, revoke-all, logout) bypass the cache and query `UserSession`. `get_user()` still checks DB user/password state. Populate only positive entries with `SESSION_CACHE_TTL=60` seconds maximum, capped by access lifetime and remaining JWT expiry. Prod `sessions` uses native RedisCache on `REDIS_URL` DB index + 1 with `KEY_PREFIX=sessions`; default cache keeps its original index. Dev/test `sessions` uses locmem. Disallow a `db` URL query parameter; specify nonnegative DB index in path. Mutation paths delete affected session IDs via `transaction.on_commit()`; failed cache deletes are logged and can let a revoked access token authenticate for at most `SESSION_CACHE_TTL` (or shorter remaining expiry). Require Redis DB-index support; do not treat this bounded staleness as immediate revocation.
- One-time codes: registration/reset/email-change use six-digit **hashed** codes, 15-min expiry, 5 max attempts. Verify does not consume; confirm consumes and mutates atomically; failed attempts commit outside inner transactions. Reissue replaces code/expiry/attempts. Reset responds identically for unknown email and queue failure (log failure, invalidate undelivered code); accepted SMTP failures are asynchronous. Registration request returns uniform 201/detail for new and active accounts; active accounts receive a security notice, not a code. Registration/email-change queue failure invalidates issued code and returns 503; accepted mail failure does not alter HTTP responses. Email change **request and confirm** require the current `password`; confirm also enforces address uniqueness. Normalize email identity consistently for registration, login, reset, and email change; enforce the selected case policy in the database and resolve collisions explicitly during migration. Self-deactivation requires the current `password`. Password similarity validator must include custom `User.name`. Issuance and verify/confirm IP throttles return 429; verification throttle permits 15 attempts/IP/minute across code flows and returns 503 on cache failure. Rate limiting hashes email/IP. Default locmem cache is per-process; production requires Redis.
- Login throttle: 30 attempts/IP and 10 attempts/IP+email per 5 minutes; successful login clears the pair counter. No global per-email login lockout. Login and code-issuance IP throttles fail open and log on cache error; issuance email throttle fails closed (503); code verification throttle fails closed (503). Password reauthentication shares a per-user counter across email-change request/confirm and self-deactivation: five wrong passwords per five minutes return 400, further attempts return 429; failure count updates and checks are atomic across concurrent requests; success clears failures; cache errors fail closed (503). Never log passwords. Superuser creation strictly requires a non-empty password before persistence. Custom `User` admin add/change forms must support email login and safe password hashing. Admin must not mutate `UserSession` directly; session changes use `SessionService` for refresh blacklisting and cache invalidation. Admin account deactivation revokes all sessions. Code verification uses row locks where supported; SQLite does not enforce them. User list is staff-only (403 otherwise), active users only, paginated (20 default, 100 max). `core/shared/client_ip.py:get_client_ip` is the sole IP source for sessions, rate limits, and future audit logging. Default `NUM_PROXIES=0` ignores X-Forwarded-For; production may set N only behind N trusted proxies. Require nonnegative `NUM_PROXIES`; validate production `REDIS_URL` scheme and hostname. N must count every hop that appends to X-Forwarded-For; the server must not also rewrite REMOTE_ADDR for the same hop. Deny direct access that bypasses trusted proxies; append, never replace, forwarding headers. Short/invalid chains fall back to validated REMOTE_ADDR; malformed REMOTE_ADDR yields no IP.
- Concurrency & Transactions: Code and security-notice mail is enqueued via `transaction.on_commit()`, never inside active `transaction.atomic()` blocks. Queue failure deletes the exact issued code and returns 503 for registration/email change; reset continues returning the uniform 200 and deletes the code. Once queued in production, SMTP failure cannot change the HTTP response: retry SMTP/network failures only, log permanent failure without secrets, and let users request a new code. Celery task receives already rendered subject/text/HTML; use JSON, no result backend, expiry bounded by remaining code lifetime, and redact broker argument representations (both OTP and recipient). Production broker uses `REDIS_URL` DB index + 2 (default cache base, sessions +1); require credentials and verified TLS for `rediss://`; use `redis://` only on a private network. Worker requires explicit `DJANGO_SETTINGS_MODULE`. Dev/test use eager tasks (SMTP failures are synchronous there); test class overrides include eager propagation. TestCase callbacks require `captureOnCommitCallbacks(execute=True)`; use TransactionTestCase to assert response status on queue failure.
- Audit: `core/models/audit_log.py` stores `AuditLog` with user UUID snapshot, `SET_NULL` FK, status choices, and event-specific allowlisted `details_json`. `core/audit/services.py:record_event` hashes unknown-login email; never store raw credentials, OTP, JWT, CSRF, or unknown email. Get IP only via `get_client_ip`, store sanitized/truncated user-agent, suppress DB/cache audit failures with `logger.exception`, deduplicate BLOCKED records per 60-second cache key. Log failed credentials and reauth outside business transactions; retain existing reauth/password/CSRF requirements. `GET /api/audit/` uses cookie auth, staff-only permission, pagination (20 default/100 max); do not register `AuditLog` in existing `/admin/`. API read-only is not DB tamper-proof: PostgreSQL append-only role/permissions and legal retention policy remain Feature 8 decisions.
- Purge: `core/registration/tasks.py:daily_maintenance_purge_task` runs at 03:00 `TIME_ZONE` via Celery Beat. Deploy one beat, shared worker and web broker; delete in batches: inactive unconfirmed users older than 48h only if verification exists, unused, expired; inactive sessions stale 30d and active sessions past their per-type absolute cap (revoke first, invalidate cache); expired audit events only when `AUDIT_RETENTION_DAYS` is a positive configured value (default `None`, no inferred legal deadline). Run Simple JWT `flushexpiredtokens`; return aggregate counts only. Never delete self-deactivated users. Simple JWT's stock flush itself is not batched.

## Run & verify

- `pdm install -G dev`; `pdm run dev`/`migrate`.
- Test execution policy: Execute tests/verify ONLY when explicitly requested by user. Standalone static checks: `pdm run lint`, `pdm run schema-check`, `pdm run migrations-check`. Full verification: `SECRET_KEY=<long-key> pdm run verify`.
- Tests harness: `tests/base.py` provides CSRF-enforcing `APIClient`, `ApiCase`/`ApiTransactionCase`, auth/email-code helpers, locmem mail, test-only MD5 hasher and long secret via class-scoped `@override_settings`, and per-test reset of default/sessions caches and mail outbox. Never enable MD5 in app settings. `post_with_commit` executes email callbacks in TestCase; use `ApiTransactionCase` for issuance failure HTTP statuses and failed-confirmation persistence. Read raw codes from `mail.outbox`, never hashed DB values; mock `django.utils.timezone.now` for expiry (locmem TTL uses monotonic time; `cache.clear()` when testing reissue). No sleeps or timing-based concurrency tests. `tests/test_rate_limit.py` has one deterministic threaded locmem counter test; it checks only same-process behavior and does not prove Redis/multi-worker safety.
- Integration harness: `tests/settings_integration.py` uses local PostgreSQL and Redis without dev settings or `.env`; isolate Redis keys with run-specific `template-auth-test:` prefixes. Before each test, clear only default-cache limiter keys (`code-request:`, `code-verify:`, `login:`, `reauth:`); clear the separate session-cache namespace normally. Never flush a shared Redis database. Within one test, use distinct email/IP inputs for independent issuance requests; preserve intentional shared counters in throttle tests. `post_with_commit(..., **extra)` forwards request metadata, including `REMOTE_ADDR`.
- Email-change recovery boundary: delete outstanding `PasswordReset` codes in the confirmed email-change transaction. Reset issuance locks and rechecks the requested user/email/active binding before issuing; concurrent email change must not leave a valid code addressed to the old mailbox. Rollback restores deleted codes.
- Deployment unverified properties: effective DB locking/concurrency, multi-worker cache throttling, real mail delivery, static files, and prod database/hosts. Do not infer production readiness from SQLite or Django check alone.
