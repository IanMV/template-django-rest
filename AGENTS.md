# Agent context

## Behavioral mandates

- **Strict technical rigor:** Zero tolerance for antipatterns, security vulnerabilities (OWASP ASVS, LGPD, race conditions, PII leaks), unhandled edge cases, or broken contracts.
- **Critical & proactive posture:** Never execute instructions blindly. Challenge assumptions, inspect actual codebase state, assess feasibility, cost, and trade-offs, and propose superior architectural alternatives.
- **AI-optimized documentation:** When creating or updating any documentation (`AGENTS.md`, `docs/*`, plans, specifications), author strictly in English, token-optimized for AI consumption: telegraphic imperative style, high semantic density, structured actionable specs, and zero conversational fluff. Always keep `AGENTS.md` synchronized with codebase boundaries and contracts.
- **No environment variable access:** Never inspect, print, read, or leak system environment variables (`env`, `printenv`, `os.environ`, real values in `.env`).
- **Conditional test execution:** NEVER run test suites (`pdm run test`, `pdm run verify`) autonomously. Run tests ONLY when explicitly commanded by the user, saving compute and time. Static checks (`lint`, `schema-check`) may run as needed.
- **Mandatory end-of-turn report:** Conclude every response with a concise report: (1) changes made, (2) technical rationale and trade-offs, and (3) pending decisions or next steps.

## Boundaries

- DRF auth template on `main`. Preserve URL order/names, response schemas/status, headers, CSRF, and cookie semantics. Small `fix:`, `refactor:`, `doc:` commits (docs last). Never push, amend, rebase, or bypass hooks. Inspect git status before editing; never discard unfamiliar changes. See `docs/CURRENT_IMPROVEMENTS.md` for current backlog. Planned features: `docs/FUTURE_FEATURES.md`; plan only.
- Route authority: `app/urls.py` composes `core/{auth,users,registration,password_reset,email_change}/urls.py`; schema/Swagger in `core/shared/urls.py` (`/api/docs/schema/`, `/api/docs/urls/`). Feature owns `views.py`, `serializers.py`, `services.py` (mutations/limits). Auth sessions use `core/auth/session_views.py`. Cross-feature imports strictly via `core/models/`, `core/shared/`, or public `core/auth/{services,authenticate,cookies,rate_limit}.py`; never internal feature modules. `core/shared/docs.py` holds schemas. Never move `core/models/`: Django app label, tables, migrations, UUID user PK, and session ID depend on location.
- Settings: `manage.py` defaults to dev (SQLite + console mail); ASGI/WSGI default to prod. Prod requires env `SECRET_KEY`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `REDIS_URL` (startup fails if absent), Secure cookies. Use `rediss://` with credentials unless Redis is on a private network; Redis must be reachable by all workers. Django 6.1 mail uses `MAILERS` with nested SMTP `OPTIONS`; dev/test already use console/locmem mailers. Prod redirects to HTTPS, defaults HSTS to one year without preload or subdomains; enable subdomains only after auditing them. `SECURE_PROXY_SSL_HEADER` trusts `X-Forwarded-Proto` only if the ingress proxy overwrites that header and direct access to Django is blocked. `ATOMIC_REQUESTS=False`: failed code attempts must persist despite HTTP 400.

## Security contracts & traps

- Cookie-only auth (`core/auth/authenticate.py`): access JWT must match active `UserSession`; unsafe requests require `X-CSRFTOKEN`. `GET /api/login/` issues CSRF cookie (204); `POST /api/login/` requires CSRF, returns only `detail` + HttpOnly access/refresh cookies; bad credentials return **401** via `LoginView.handle_exception`. Access cookie name follows `SIMPLE_JWT.AUTH_COOKIE` (default `access_token`), refresh is `refresh_token`; SameSite=Lax, Secure in prod. Cookie ops belong in `core/auth/cookies.py`.
- Refresh & sessions: `POST /api/refresh/` enforces CSRF even after access expiry; `SessionService.refresh_tokens` checks refresh JTI, rotates both tokens, and updates `last_activity` under `atomic` + `select_for_update`. SQLite ignores row locks: do not infer concurrency safety from SQLite. Login revokes existing cookie session; matching user/device/IP replaces session. Logout revokes current; revoke-all, self-deactivation, password reset, and confirmed email change revoke all and clear cookies. Revocation blacklists refresh tokens and deactivates sessions; access fails session lookup. Foreign session IDs return 404; current session cannot be deleted via `/api/sessions/<id>/`. Do not restore unrouted `UserDetailView`/`UserUpdateSelfView`.
- One-time codes: registration/reset/email-change use six-digit **hashed** codes, 15-min expiry, 5 max attempts. Verify does not consume; confirm consumes and mutates atomically; failed attempts commit outside inner transactions. Reissue replaces code/expiry/attempts. Reset responds identically for unknown email. Email change verifies current password and address uniqueness. Password similarity validator must include custom `User.name`. Throttles: 429; issuance failure: 503. Rate limiting hashes email/IP. Default locmem cache is per-process; production requires Redis.
- Login throttle: 30 attempts/IP and 10 attempts/IP+email per 5 minutes; successful login clears the pair counter. No global per-email login lockout. Code verification uses row locks where supported; SQLite does not enforce them. `core/shared/client_ip.py:get_client_ip` is the sole IP source for sessions, rate limits, and future audit logging. Default `NUM_PROXIES=0` ignores X-Forwarded-For; production may set N only behind N trusted proxies. N must count every hop that appends to X-Forwarded-For; the server must not also rewrite REMOTE_ADDR for the same hop. Deny direct access that bypasses trusted proxies; append, never replace, forwarding headers. Short/invalid chains fall back to validated REMOTE_ADDR; malformed REMOTE_ADDR yields no IP.
- Concurrency & Transactions: External I/O (email sending via `send_email_token`) must run via `transaction.on_commit()`, never directly inside active `transaction.atomic()` blocks.

## Run & verify

- `pdm install -G dev`; `pdm run dev`/`migrate`.
- Test execution policy: Execute tests/verify ONLY when explicitly requested by user. Standalone static checks: `pdm run lint`, `pdm run schema-check`, `pdm run migrations-check`. Full verification: `SECRET_KEY=<long-key> pdm run verify`.
- Tests harness: `tests/base.py` provides CSRF-enforcing `APIClient`, `ApiCase`/`ApiTransactionCase`, auth/email-code helpers, locmem mail, and per-test cache reset. For fast test runs (<3s), use `PASSWORD_HASHERS = ["django.contrib.auth.hashers.MD5PasswordHasher"]` scoped via `@override_settings` in test classes (never in `base.py`). Read raw codes from `mail.outbox`, never hashed DB values; mock `django.utils.timezone.now` for expiry (locmem TTL uses monotonic time; `cache.clear()` when testing reissue). Use `TransactionTestCase` for failed-confirmation persistence. No sleeps/concurrency tests.
- Deployment unverified properties: effective DB locking/concurrency, multi-worker cache throttling, real mail delivery, static files, and prod database/hosts. Do not infer production readiness from SQLite or Django check alone.
