# Agent context

- Purpose: DRF authentication template; preserve URL, response, cookie, and status contracts unless fixing a documented security defect. Work on `main`; commit each logical fix separately (`fix:`), documentation last (`doc:`); never push, amend, rebase, or bypass hooks.
- Entrypoints: `manage.py` loads `app.settings.dev`; `app/asgi.py` and `app/wsgi.py` load `app.settings.prod`. `app/settings/base.py` owns DRF, CSRF, JWT, and mail defaults; `dev.py` uses console mail/SQLite, `prod.py` takes `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, optional `DATABASE_NAME`, and `SECRET_KEY` from the environment, defaults to SQLite, and requires Secure auth/CSRF/session cookies. `app/urls.py` is the actual route authority; README route descriptions are stale.
- Routing and ownership: `core/views/{user,registration,password_reset,email_change}.py` orchestrate requests; `core/serializers/` validate inputs; `core/services/` manage mutations, session state, and cache limits; `core/models/one_time_code.py` supplies shared verification/attempt logic; `core/authenticate.py` verifies access JWT + active `UserSession` and enforces CSRF on authenticated unsafe requests; `core/utils/cookies.py` is the single source of cookie names/options/deletion; `core/exceptions.py` defines HTTP 503 for request-flow failures. `UserDetailView` and `UserUpdateSelfView` exist but are not routed. User PK is UUID; session PK is integer.
- Auth sequence: `GET /api/login/` sets the CSRF cookie (204); subsequent `POST /api/login/` **requires** `X-CSRFTOKEN`, creates access and refresh cookies, returns only `detail` (JWTs removed from JSON), and deactivates the prior cookie session when present. Login with the same user/device/IP also replaces existing active sessions for that tuple. Authenticated unsafe API requests require CSRF; `POST /api/refresh/` explicitly requires CSRF even when the access token has expired and rotates tokens inside an atomic transaction with `select_for_update` (row locking depends on the DB backend). It checks the refresh JTI against the active session, then replaces both JTIs; stale tokens cannot revive it. Access JWT authentication rejects an inactive session. Cookies: configurable access name (default `access_token`), fixed `refresh_token`, `csrftoken`; auth cookies HttpOnly, SameSite=Lax, Secure in production. Client must send credentials and CSRF header for unsafe requests.
- Sessions: logout (`POST /api/me/logout/`) revokes current refresh/session and deletes cookies; `POST /api/me/revoke-sessions/` and `POST /api/me/deactivate/` revoke sessions and delete cookies; `DELETE /api/sessions/<int:session_id>/` rejects deletion of the current session; `GET /api/sessions/` marks current by access JTI. Password reset and confirmed email change revoke **all** sessions; email change also deletes response cookies. Revocation marks `UserSession` inactive and blacklists outstanding refresh tokens; access JWTs are rejected by the session lookup. `last_activity` changes on refresh.
- Code workflows: registration `/api/registration/{request,verify,confirm}/`, reset `/api/password-reset/{request,verify,confirm}/`, email change `/api/email-change/{request,verify,confirm}/`. Six-digit secrets are hashed at rest; 15-minute lifetime; five wrong checks exhaust a code. Successful `verify` does not consume the code; wrong codes increment attempts. `confirm` uses `select_for_update` (effective row locking requires a supporting DB), atomically mutates user + consumes code, and commits invalid-attempt increments. Keep `ATOMIC_REQUESTS` disabled or preserve failed-attempt commits explicitly. New registration requests replace the old code and reset expiry/usage; reset and email-change requests also replace old codes. Reset only issues for active users, without disclosing whether the email exists. Email change requires current password on confirm and rechecks new-email uniqueness. Registration/reset password validation includes the relevant user's name/email for similarity checks.
- Abuse limits: `core/services/rate_limit.py` uses Django cache (`cache.add` for issuance, `cache.incr` for login), keyed by SHA-256 email/IP; code requests allow one per email per scope per 60 s and one per IP per scope per 2 s; login allows ten per email and thirty per IP per five minutes. Default local-memory cache is process-local: production with multiple workers/hosts **must** configure a shared cache or limits are not global. `REMOTE_ADDR` is used, not untrusted forwarded IP headers. Rate limiting returns HTTP 429.
