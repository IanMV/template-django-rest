# Agent context

- Purpose: DRF authentication template; preserve routes, response bodies/status, headers, CSRF, and cookie contract. Branch `main`; use `refactor:` for feature moves, `fix:` for defects, `doc:` last; no push, amend, rebase, or hook bypass.
- Feature boundaries: `core/{auth,users,registration,password_reset,email_change}/` own `urls.py`, `views.py`, `serializers.py`, `services.py`; `core/auth/session_views.py` isolates the larger session subflow. A feature imports `core/models/`, `core/shared/`, or the public service/security API under `core/auth/`; it does not import another feature's internals. Views validate/call services/respond; mutation, transaction, and limits belong in services. `core/models/` remains in place to preserve Django app label, tables, migration references, and user/session identity (UUID user, integer session); never move models as part of feature organization. `core/admin.py` registers existing models. `app/urls.py` composes feature URL lists in the original order; `core/shared/urls.py` owns schema and Swagger endpoints. `core/shared/{docs,exceptions,response_messages,email_token_sender}.py` and `shared/permissions/` are cross-feature utilities.
- Entrypoints: `manage.py` defaults to `app.settings.dev`; ASGI/WSGI default to `app.settings.prod`. `app/settings/base.py` configures auth class `core.auth.authenticate.CustomAuthentication`, CSRF, JWT, and mail; dev uses SQLite/console mail, production takes `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, optional `DATABASE_NAME`, and `SECRET_KEY` from the environment, defaults to SQLite, and sets Secure auth/CSRF/session cookies. Keep `ATOMIC_REQUESTS` disabled: invalid-code increments must commit even when response is 400.
- Auth: `core/auth/views.py` handles login/refresh/logout; `auth/session_views.py` handles session listing/deactivation; `auth/services.py` owns token rotation, blacklist, session state, and login. `GET /api/login/` bootstraps the CSRF cookie (204); `POST /api/login/` requires `X-CSRFTOKEN`, returns `detail` without JWT JSON, sets access/refresh cookies, and revokes an existing cookie session. Same-user/device/IP login replaces matching sessions. `POST /api/refresh/` requires CSRF even with expired access token; the service locks the session with `select_for_update` inside `atomic`, checks refresh JTI/active status, rotates tokens, updates both JTIs and `last_activity`. Effective row locking depends on backend (SQLite does not provide it). `auth/authenticate.py` validates access JWT against active `UserSession` and enforces CSRF on authenticated unsafe methods; `auth/cookies.py` centralizes access name (default `access_token`), fixed `refresh_token`, cookie flags, and deletion. Cookies are HttpOnly/SameSite=Lax, Secure in production. `auth/rate_limit.py` hashes email/IP for cache keys; code issuance is limited per scope/email (60 s) and IP (2 s), login per email (10/5 min) and IP (30/5 min), returning 429. `REMOTE_ADDR` is used rather than forwarded headers; multi-worker production requires shared cache (default local-memory cache is process-local).
- Users/sessions: `core/users/` handles profile/list, self-deactivation, and revoke-all; calls public `auth.services.SessionService` for session invalidation and `auth.cookies.clear_auth_cookies` for response cleanup. `POST /api/me/logout/` revokes current session; `POST /api/me/revoke-sessions/` and `POST /api/me/deactivate/` revoke all; `DELETE /api/sessions/<int:session_id>/` refuses current-session deactivation. Password reset and confirmed email change revoke all sessions; email change also clears response cookies. Revocation deactivates session records and blacklists outstanding refresh tokens; access tokens fail the active-session lookup. Removed unused, unrouted `UserDetailView` and `UserUpdateSelfView`; do not restore undocumented routes implicitly.
- One-time codes: each of `core/{registration,password_reset,email_change}/` has request/verify/confirm endpoints and local services/serializers. `core/models/one_time_code.py` hashes six-digit codes, expires after 15 min, exhausts after five invalid checks; successful verify does not consume, invalid verify increments attempts. Confirmation takes `select_for_update`, updates the user and marks used atomically; invalid attempts commit outside inner atomic. New requests replace old codes (including expiry/usage); reset only sends for active users and returns the same success response for unknown email. Email-change confirmation checks current password and new-email uniqueness. Registration/reset password validators receive user attributes for similarity checks. `shared.exceptions.ServiceUnavailable` produces HTTP 503 for issuance failures.
- Verification: `python -m compileall core app`; `pdm run ruff check`; `SECRET_KEY=<value> pdm run python manage.py check`; `SECRET_KEY=<value> pdm run python manage.py makemigrations --check --dry-run`; `pdm run python manage.py test`; deploy checks with `DJANGO_SETTINGS_MODULE=app.settings.prod SECRET_KEY=<value> ALLOWED_HOSTS=<host>`. Compare migrations/models to baseline before feature moves. `pyproject.toml`/`pdm.lock` omit imported runtime packages `rest_framework_simplejwt` and `user_agents`; current environment lacks these and Ruff, so check/test/makemigrations cannot run without dependency changes. No behavior tests exist and CI does not run tests. Production still needs a mail backend, static serving, suitable durable DB, real hosts/origins, and shared cache; avoid assuming local-memory throttles work across workers.
